1. Architecture
Two independent ingestion pipelines (tickets, logs) feed one project-scoped data store. Two clustering engines and cross-source correlation turn that into scored, explainable clusters and patterns. An optional narrative layer sends already-computed data through a local LLM bridge to add plain-English write-ups on top — nothing downstream depends on it being available.

2. How It Works — End to End
1
Upload & Map
Drop in a CSV/Excel export from any ITSM tool, match its columns to fields the app understands, choose a date format, and confirm — nothing is imported until you review the mapping.
↓
2
Automatic Sensitive-Data Scan
Every uploaded row is scanned for card numbers, IBANs, phone numbers and similar patterns as it comes in — see the Sensitive Data Report.
↓
3
Run a Clustering Engine (A and/or B)
Traditional ML and Generative AI each group similar tickets independently — results are kept separate per engine, so running one never overwrites the other.
↓
4
Review Problem Clusters
Each cluster carries a confidence score, a trend (rising/falling/stable), and — where the data supports it — a regional breakdown. High-confidence, recurring, rising clusters get flagged as Problem Candidates.
↓
5
Drill Down (optional)
Re-cluster just one cluster's own tickets into finer sub-groups when a group looks too broad to act on directly.
↓
6
Lookup Tools
Smart Search (semantic search), Smart Assign (queue suggestion), and Possible Duplicates all run on demand, independent of the main clustering runs. (The Sensitive Data Report is a review of step 2's automatic scan, not something you separately run.)
↓
7
Generate AI Insight — one click, or copy/paste
Every "✨ Generate with Copilot Bridge" button sends a prompt built from real data on this machine to your local Copilot HTTP Bridge and saves the reply automatically — cluster summaries, trend hypotheses, resolution drafts, formal Problem Records, duplicate explanations, log pattern narratives, cross-source incident stories, cross-cluster strategic analysis, and an instant dashboard briefing. The original manual flow (copy a prompt, paste into your own Copilot chat, paste the answer back) still works everywhere as a fallback if the bridge isn't running.
↓
8
Export Anything
Every results page — Problem Clusters, Global Clustering, Duplicate Candidates, Log PII Alerts, Log Patterns, Cross-Source Patterns — has a Download CSV button, respecting whatever filter is currently applied.

Clustering Engines
FeatureWhat it doesExample
Traditional ML ATF-IDF + HDBSCAN groups tickets that share vocabulary — fast, explainable, fully on-prem.Run on 1,200 incidents → get a "VPN Login Failures" cluster of 84 tickets at 91% confidence.
Generative AI BA local sentence-embedding model groups tickets by meaning, not just shared words."Batch job stuck" and "nightly process not finishing" land in the same cluster despite sharing zero keywords.
Statistical Trend TestRising/Falling isn't a fixed "±25% more/fewer" cutoff — it's an exact binomial test (the correct form of a Poisson rate-ratio test for equal-length windows) comparing a cluster's earliest and most recent thirds, so small clusters no longer get flagged as trending on single-ticket noise.A 26-vs-14 ticket split (p=0.081) now correctly shows Stable — the old fixed-ratio rule would have called that "Rising" purely from sample-size noise.

4. The Two Clustering Engines
Both are genuinely AI — Traditional ML (statistical/classical) and Generative AI (embedding-based) are both branches of the same AI family tree. The choice is about cost, infrastructure, and semantic depth, not "AI vs. no AI." Both run live and fully on this machine today — neither is waiting on external API access.
DimensionApproach A · Traditional MLApproach B · Generative AI
How it worksTF-IDF word-frequency vectors + HDBSCAN density clusteringLocal sentence-embedding model (all-MiniLM-L6-v2) + cosine-similarity clustering
Semantic understandingModerate — needs vocabulary/stem overlapStrong — understands paraphrasing and context
CostOne-time build cost, no per-call feesNo per-call fees either — runs a local model, not a hosted API
Data privacyFully on-premFully on-prem — a hosted Azure OpenAI endpoint remains an optional future upgrade, not a requirement
ExplainabilityTransparent, rule-based — easier to justify to an auditorLess transparent (embedding-space "black box")
Best fitFast, explainable first pass; good for audit-sensitive reviewPrimary recommendation for ticket text, since reporters reword the same issue differently — semantic matching catches what keyword overlap misses
Practical guidance: run Traditional ML first as a fast baseline, then Generative AI for the semantic pass. Both are safe to run on the same data — nothing is overwritten between engines, only within the same engine on a re-run.
5. Assumptions Made
  • Uploaded data has at least one genuinely free-text field (a title/description) — clustering quality depends directly on how descriptive that text is; a file of only short codes will cluster poorly.
  • Queue, offering, application, country, and similar fields are treated as optional. When your source data doesn't map to them, the features that depend on them (queue categorization, regional trend breakdown, app filters) simply have nothing to show — this isn't an error state.
  • A single date format applies consistently to every row within one uploaded file, chosen once during the mapping step.
  • At least 8 tickets are needed before any cluster can form. Small datasets, or a narrow "Run on" scope (a single upload, a single offering), may legitimately produce zero clusters.
  • The local sentence-embedding model is treated as a reasonable stand-in for a hosted Azure OpenAI embeddings endpoint — good for general English support-ticket text, but not fine-tuned to any organization's specific acronyms or internal system names.
  • Sensitive-data scanning (regex + Luhn/IBAN checksum + phone-number parsing) is assumed to catch the common, well-structured formats — card numbers, IBANs, phone numbers — not a certified DLP/PII product covering every possible sensitive-data shape.
  • A ticket pair is assumed to be a likely duplicate only when similarity is very high (≥92%) and close in time (7 days) and shares a reporter or application — high text similarity alone is treated as insufficient, since two distinct-but-related issues can still read as similar.
  • Queue-suggestion voting trusts whatever queue values already exist in your uploaded data as ground truth — if those source labels are inconsistent, suggestions inherit that inconsistency.
  • AI Summary, Trend Explanation, Resolution Draft, Problem Record, Strategic Narrative, Search Synthesis, Duplicate Explanation, Pattern Narrative, and Incident Narrative all assume a human in the loop for review, even though generation itself is now automatic: this app builds a prompt from real data and sends it to the Copilot HTTP Bridge — a local VS Code extension exposing the signed-in Copilot chat model over plain HTTP on this machine — and saves the reply, but nothing is treated as final until a person reads it. The original manual copy/paste flow remains as a fallback everywhere the bridge is used, for when it isn't running.
  • The Copilot HTTP Bridge is assumed to be a single developer's local, opt-in convenience, not a shared service — it's only reachable while that person's VS Code Extension Development Host window is open on that machine, has no authentication of its own, and is scoped to one Copilot seat's rate limits. It is not assumed to be an architecture for multi-user production AI generation as-is.
  • Log PII Scan assumes phone-number detection is worth trading away by default at log scale — most log lines contain digits (timestamps, ports, IDs) that would trigger the phonenumbers check on nearly every line; it's an opt-in toggle per source rather than left on and slow.
  • Find Patterns assumes a recent, bounded slice of a file (~5MB) is representative enough to be useful — it's explicitly not an exhaustive analysis of an entire 100GB file the way Log PII Scan is; that trade-off is what keeps it fast enough to run synchronously in a page request.
  • SQLite is assumed sufficient for this scale of use (single team, moderate ticket volumes); a production multi-user rollout would need PostgreSQL, per the original proposal.
6. Known Limitations
  • The Copilot HTTP Bridge has no authentication. Anything running on the same machine can call it — acceptable for a single developer's local dev box, not a design suited to a shared server without a network-level restriction (e.g. binding to localhost only, which it already does by default).
  • The bridge is only live while its VS Code Extension Development Host window stays open — it is not an always-on background service. Every generate call fails fast with a clear, caught error (never a silent hang or a corrupted save) if the window is closed; the manual copy/paste fallback still works everywhere in that case.
  • Routing application traffic through a personal Copilot seat programmatically is a different usage pattern than interactive coding assistance — worth checking against your organization's Copilot/GitHub license terms before relying on this bridge beyond a demo or single-developer convenience.
  • Bridge output is non-deterministic and unreviewed by default for the auto-saving features (AI Summary, Trend Explanation, Pattern Narrative, Incident Narrative, Search Synthesis, Duplicate Explanation) — the same prompt can produce a differently-worded answer on a re-run, and nothing blocks a factually wrong generation from being saved automatically. Resolution Draft and Problem Record are deliberately NOT auto-saved for this reason — Generate renders a draft into a textarea, and a person must explicitly Save after reviewing it.
  • Single Copilot seat, single-seat rate limits. Generating for many clusters back-to-back in a short window can hit Copilot's own usage limits — the bridge surfaces that as a normal generation failure, not a silent retry loop.
  • Re-running an engine replaces its previous top-level results, not merges with them — by design, so a stale run never lingers, but it means any manual edits tied to the old clusters (like resolution notes) don't automatically carry over to the new ones if the cluster boundaries shift.
  • Resolution notes are tied to a specific cluster row. If you reset or re-run a pipeline and the cluster IDs change, previously saved notes stay on the old (now-gone) cluster rather than following the "same" issue to its new cluster — this is the clearest current gap between "notes exist" and "notes are durable."
  • Queue suggestions need enough labeled data to vote from. With very few or heavily skewed existing queue values, suggestions get thin and less trustworthy — treat low-agreement suggestions as a starting guess, not a verdict.
  • No integration back into an external ITSM tool. Promoting a Problem Candidate into an actual ServiceNow/Jira Problem record is a manual step outside this app today — nothing here creates or updates records elsewhere.
  • Everything is user-triggered. There's no background scheduler re-running pipelines or rebuilding indexes as new tickets arrive — you decide when to re-scan, re-cluster, or rebuild. Scheduled and Continuous log sources are the one exception, and even those rely on something external (Windows Task Scheduler, a second Windows Service) actually invoking them — nothing inside this app schedules itself.
  • Clipboard-copy conveniences (e.g. "Copy Prompt for Copilot") depend on browser clipboard permissions — locked-down or automated browser environments may block them; paste manually if so.
  • No granular in-project permissions yet. Projects isolate data from each other, but anyone with access to a project can see and edit everything inside it — there's no per-user role restriction within a single project.
  • Find Patterns doesn't cover directory/NAS sources yet. Which file to analyze (or how to merge several) is a real design question left unresolved — pattern discovery is path/upload sources only for now; Log PII Scan already covers directory sources fully.
  • No trend/anomaly detection for logs yet — Find Patterns surfaces recurring patterns as they stand right now, not whether a pattern is newly spiking or fading, the way ticket clusters show Rising/Falling. That needs reliable per-line timestamp parsing across arbitrary log formats, deliberately not attempted in this first phase.
  • A window of near-identical log lines can under-cluster. If almost every line in the analyzed slice shares the same wording (little vocabulary left to distinguish templates once shared boilerplate is naturally downweighted), Find Patterns can call the whole window "unclustered" instead of finding the one dominant pattern — confirmed harmless (nothing is lost or mis-shown), just less useful for that specific edge case. Realistic, mixed-content log windows aren't affected.
